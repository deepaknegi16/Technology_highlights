Estimation formulas + worked example

The trick: 1 day ≈ 105 seconds (86,400). All estimation is multiplication with round numbers — say the units out loud.

QuantityFormulaRule of thumb
Average QPSDAU × actions/user/day ÷ 105 s10M DAU × 10 actions ≈ 1,000 QPS
Peak QPSaverage × peak factor2–3× normal; 10×+ for events/flash sales
Storageitems/day × size × days × replication×3 for replication; ×1.5 for indexes/overhead
BandwidthQPS × payload size1k QPS × 100 KB = 100 MB/s ≈ 1 Gbps
Cache size~20% of hot data (80/20 rule)enough for ~80%+ hit ratio on Zipf traffic
Worked example — photo app, 10M DAU:
  • Writes: 10M × 2 photos/day ÷ 105 = 200 uploads/s (peak ~600/s).
  • Reads: 100:1 read ratio → 20k views/s (peak 60k/s) — design for the read path.
  • Storage: 20M/day × 2 MB = 40 TB/day → ~14 PB/yr ×3 replicas ≈ 42 PB → object store + CDN, never a DB.
  • Metadata: 20M/day × 1 KB = 20 GB/day → ~7 TB/yr — one sharded DB is fine.
  • Cache: 20% of daily hot metadata ≈ a few hundred GB → small Redis cluster.
Interviewer will probe
  • Why divide by 105 not 86,400? → Round numbers; estimation cares about the exponent, not the mantissa.
  • What peak factor for a ticket on-sale? → 10–100×: demand compresses into the first minute.
  • KB vs KiB pedantry? → Say "I'll use powers of 10 for estimation" and move on.

SLA math — nines & composition

Two formulas: serial chains multiply availabilities (chain is weaker than its weakest link); parallel redundancy multiplies the unavailabilities.

NinesAvailabilityDowntime / yearDowntime / month
2 nines99%3.65 days~7.3 h
3 nines99.9%8.77 h~43.8 min
4 nines99.99%52.6 min~4.4 min
5 nines99.999%5.26 min~26 s
Composite availability.
  • Serial (A depends on B): Atotal = A × B. Three 99.9% services in a chain → 99.7% (~26 h/yr).
  • Parallel (either of two replicas serves): A = 1 − (1−a)². Two 99% nodes → 99.99% — if failures are independent.
  • Each extra serial dependency costs nines; each independent replica buys them. Correlated failures (same AZ, same deploy) void the parallel math.
Interviewer will probe
  • Your SLA is 99.9% but you depend on a 99.9% DB — possible? → Only with redundancy or graceful degradation on DB failure.
  • Why not promise 5 nines? → 26 s/month means no human in the loop and multi-region active-active; cost explodes per nine.
  • SLI vs SLO vs SLA? → Measurement vs internal target vs external contract with penalties.

SQL vs NoSQL (and which NoSQL family)

PickWhenBecause
SQL (Postgres/MySQL)Relations, transactions, flexible/unknown queries, <~10 TBACID, joins, mature tooling; scales further than people admit
Key-value (Dynamo/Redis)Get/put by key at huge scale, predictable low latencyPartitions trivially; no query flexibility to lose
Wide-column (Cassandra)Write-heavy, time-series-ish, known access patternsLSM writes + linear scale-out; queries must match table design
Document (MongoDB)Self-contained aggregates, evolving schemaObject maps to one document; weak at cross-document joins
Graph (Neo4j)Many-hop relationship traversalsJoins of depth N are the workload itself

Default answer: Postgres until a specific number (write QPS, data size, or access pattern) forces something else.

"I'd start with Postgres — our scale fits. If writes outgrow one leader or the access pattern is pure key-lookup at millions of QPS, I'd move that table to DynamoDB/Cassandra, chosen by access pattern first."

B-tree vs LSM tree

AxisB-tree (Postgres, MySQL)LSM (Cassandra, RocksDB)
WritesIn-place page update — random I/OAppend to memtable → flush SSTables — sequential I/O, much faster
ReadsOne tree walk — predictable, fastMay check memtable + several SSTables (bloom filters help)

Default answer: B-tree unless the workload is write-dominated (logs, events, metrics) — then LSM.

"LSM turns random writes into sequential appends, trading read amplification and compaction cost — that's why write-heavy stores like Cassandra use it."

AxisKey-range (HBase, Spanner)Hash (Dynamo, Cassandra)
Range scansEfficient — adjacent keys colocatedImpossible without scatter-gather

Strong vs eventual consistency

ModelGuaranteePriceRequired for
Strong (linearizable)Every read sees the latest writeCoordination on every op: latency + reduced availability under partitionMoney, inventory, seat allocation, uniqueness (usernames)

"Like-counts can be seconds stale; the seat map cannot oversell — so I pay for strong consistency only on the booking write."

3️⃣ 16 Designs in Recipe Form

URL shortener

Scale assumption: 100M new URLs/month (~40 writes/s), read:write 100:1 → 4k redirects/s; ~3 TB over 5 years.

Recipe.
  • Key generation: counter + base62, ranges leased per app server — unique by construction, no collisions.
  • Storage: one KV table code→long_url, hash-sharded by code — only query is exact lookup.
  • Read path: Redis cache-aside — Zipf traffic means a small cache absorbs 90%+ of redirects.
  • Redirect: 302 not 301 — keeps clicks on your servers for analytics and expiry.
  • Analytics: click event → Kafka, fire-and-forget — never on the redirect's latency path.

Key trade-offs

  • Counter vs hash keys: counter when you can run a range-lease service; hash (with conditional-insert retry) when you want zero coordination + dedupe.
  • 301 vs 302: 301 offloads traffic to browser caches; pick 302 whenever analytics or expiry is a requirement.
Interviewer will probe
  • Code length? → 627 ≈ 3.5T codes; 7 chars lasts millennia at this rate.
  • Sequential codes are enumerable? → XOR with a secret, or pre-generated random key pool (KGS).
  • 100× reads? → Nothing interesting breaks: more cache + app replicas; DB sees only misses.

Full walkthrough: URL shortener

Rate limiter (as a service)

Scale assumption: 50k RPS across ~50 gateways, ~10M active keys, budget 1–2 ms per check.

Recipe.
  • Algorithm: token bucket — 2 numbers per key (tokens, last_refill), bursts allowed by design.
  • State: Redis cluster sharded by key — shared across all gateway nodes.
  • Atomicity: Lua script does read-refill-decide-write in one round trip — no check-then-set race.
  • Placement: in the API gateway/middleware, before auth-heavy work.
  • Response: 429 + Retry-After header; expose remaining-quota headers.
  • Rules: config service pushes limits (per user/IP/tenant/endpoint) to gateways; cache rules locally.

Key trade-offs

  • Fail open vs fail closed on Redis outage: fail open for product APIs (limiter must not be the outage); fail closed for auth/abuse endpoints.
  • Central Redis vs local counters: local (limit ÷ N nodes) is approximate but zero-latency; central is exact — hybrid: local pre-filter, central authority.
Interviewer will probe
  • Race with two gateways checking at once? → Lua script is atomic on the shard — single-threaded Redis serializes it.
  • Hot key (one huge tenant)? → Split their bucket into K sub-buckets across shards, sum approximately.
  • Why not sliding-window log? → O(events) memory per key; token bucket is O(1) with equivalent fairness.

Full walkthrough: Rate limiter

Unique ID generator

Scale assumption: 10k+ IDs/s across many nodes; IDs must be unique, roughly time-sortable, 64-bit.

Recipe.
  • Layout (Snowflake): 41 bits timestamp-ms + 10 bits machine id + 12 bits sequence → 4096 IDs/ms/node, ~69 years.
  • Machine id: assigned via ZooKeeper/etcd lease at startup — never two nodes with the same id.
  • Clock skew: on clock going backwards, refuse to issue (wait) — never reuse a timestamp.
  • Alternative: UUIDv7 — time-ordered, no coordination, 128 bits; use when 64-bit isn't required.
  • Alternative: DB ranges — each node leases blocks of 1M ids; simple, IDs not time-ordered across nodes.

Key trade-offs

  • Snowflake vs UUIDv4: k-sorted IDs keep B-tree inserts append-like; random UUIDs fragment indexes — pick Snowflake/UUIDv7 for DB primary keys.
  • Coordination at startup (machine id) vs per-request: pay coordination once per boot, never per ID.
Interviewer will probe
  • Why time-sortable? → Order-by-id ≈ order-by-time: free pagination cursors and index locality.
  • NTP steps the clock back 500 ms? → Block issuance until the clock catches up, or bump sequence into a logical clock.
  • IDs leak creation rate? → Yes (German-tank problem) — obfuscate if commercially sensitive.

Full walkthrough: Unique ID generator

Distributed KV store (Dynamo-style)

Scale assumption: 100k ops/s, 10 TB, always-writable, tunable consistency; N=3 replicas.

Recipe.
  • Partitioning: consistent hashing with virtual nodes — add/remove a node moves ~1/N of keys.
  • Replication: N=3 successors on the ring; any node can coordinate a request.
  • Consistency: quorum R+W>N (2+2>3 typical); tune per use (W=1 fast writes, R=1 fast reads).
  • Availability: sloppy quorum + hinted handoff — writes land on stand-ins during failures.
  • Conflicts: vector clocks (or LWW if losing writes is acceptable); read repair + Merkle-tree anti-entropy.
  • Membership: gossip protocol — no central coordinator to fail.

Key trade-offs

  • Quorum vs single-leader: pick quorum for always-writable AP behavior; pick a leader when you need transactions or ordered writes.
  • LWW vs vector clocks: LWW is simple but silently drops concurrent writes — fine for caches, wrong for carts.
Interviewer will probe
  • Why virtual nodes? → Even load and even redistribution when hardware is heterogeneous.
  • Is R+W>N linearizable? → No — sloppy quorums and partial writes break it; it's "usually reads latest".
  • Node rejoins after an hour? → Hinted handoff replays missed writes; Merkle diff catches the rest.

Full walkthrough: Leaderless replication & quorums

Chat (WhatsApp)

Scale assumption: 500M DAU, 50B msgs/day ≈ 600k msg/s avg; ~1M concurrent connections per gateway box possible, so ~500–1000 WS gateways.

Recipe.
  • Transport: WebSocket gateways (stateless app tier can't hold connections — this tier is stateful by nature).
  • Registry: Redis user_id→gateway_id, written on connect, TTL'd by heartbeat — how messages find the receiver.
  • Persist-then-push: write to message store first, then route — device ack drives delivery receipts.
  • Storage: Cassandra/HBase, partition by conversation_id, cluster by message_id (time-ordered) — write-heavy, range-read by conversation.
  • Ordering: per-conversation sequence from the partition owner — global order is neither possible nor needed.
  • Offline: undelivered flag + push notification via APNs/FCM; client syncs missed messages on reconnect by last-seen id.
  • Groups: fan-out server-side to each member's gateway; large groups get pull-on-open past a size threshold.

Key trade-offs

  • Registry lookup vs pub/sub broadcast: registry is exact routing at lookup cost; pub/sub per-user channels simplify code but add broker hops.
  • Sent vs delivered vs read: one tick = server persisted, two = device acked — separate acks, separate failure modes.
Interviewer will probe
  • Gateway dies with 1M connections? → Clients reconnect via LB with jittered backoff; registry entries expire; messages queue as undelivered.
  • Presence at 500M users? → Heartbeat every ~30 s into registry TTL; fan out presence lazily (only to open conversations).
  • E2E encryption impact? → Server routes ciphertext blobs; server-side search/moderation of content becomes impossible.

News feed (Twitter/Instagram)

Scale assumption: 200M DAU, 1B feed reads/day (~10k QPS, peak 30k), 100M posts/day; avg 200 followers, max 100M.

Recipe.
  • Hybrid fan-out: push (write to each follower's inbox) for normal authors; pull at read time for authors > ~100k followers.
  • Inbox: Redis sorted set per user of ~800 post IDs — IDs only; hydrate post content from a post cache at read.
  • Fan-out: async via queue — posting returns instantly; lag of seconds is invisible.
  • Read: merge inbox + celebrity pull + ranking; cursor pagination by post_id (time-sortable Snowflake IDs).
  • Storage: posts in sharded store by author_id; social graph service for follower lists.
  • Skip inactive users during fan-out — build their feed lazily on next visit.

Key trade-offs

  • Push vs pull: push buys fast reads with write amplification; pull is write-cheap but read-slow — the threshold follower count is the design.
  • IDs-only inboxes vs full posts: IDs cost one hydration hop but make edits/deletes trivial and inboxes 100× smaller.
Interviewer will probe
  • Celebrity posts, 100M followers — why not push anyway? → 100M writes for one tweet, minutes of lag, hot-spotting — one post = a small outage.
  • Deleted post still in inboxes? → Inboxes hold IDs; hydration filters dead IDs — no 100M-inbox cleanup.
  • Offset vs cursor pagination? → Feed shifts while paging; cursor (last seen post_id) is stable, offset double-shows items.

Notification system

Scale assumption: 100M notifications/day (~1–10k/s bursty) across push, email, SMS; third-party providers do final delivery.

Recipe.
  • Ingest: one internal API — services publish notification events to a queue; never call providers inline.
  • Pipeline: workers per channel (APNs/FCM, SES, Twilio) consume queues, apply rate/retry per provider.
  • Preferences + quiet hours: check user settings service before send — a hard gate, not a filter after.
  • Dedupe: idempotency key (event_id + user + channel) in Redis — retries and double-publishes send once.
  • Templates: content rendered from template + payload at send time; localization here.
  • Tracking: provider webhooks (delivered/bounced/opened) feed back into a status store; DLQ for failures.

Key trade-offs

  • At-least-once + dedupe vs at-most-once: duplicate pushes annoy, missing "your ride is here" is worse — dedupe key makes at-least-once safe.
  • Provider failover: multi-provider per channel with health-based routing vs simplicity of one — SMS/email deserve two, push can't (APNs is the only door to iOS).
Interviewer will probe
  • Provider is down 30 min? → Queue buffers; retry with backoff; alert on queue age; fail over where a second provider exists.
  • User gets 50 notifications in a burst? → Batch/digest window per user + per-user rate cap.
  • Ordering across channels? → Don't promise it; channels are independent pipelines.

Typeahead / autocomplete

Scale assumption: 10B queries/day, ~5 keystrokes each → ~500k lookups/s peak; p99 < 50 ms end-to-end.

Recipe.
  • Precompute: offline pipeline aggregates query logs → top 5–10 suggestions per prefix, rebuilt daily.
  • Serve: prefix→suggestions as a flat KV/trie snapshot in memory, sharded by prefix — a lookup is one GET.
  • Cache at the edge: CDN/browser cache short prefixes; client caches and filters locally as the user types.
  • Freshness fast lane: streaming counter (last hours) merged with the daily batch for trending queries.
  • Client: debounce keystrokes (~100–200 ms), cancel stale requests.

Key trade-offs

  • Precomputed top-K vs live trie ranking: precompute makes serving trivial and fast; you accept hours of staleness (patched by the fast lane).
  • Shard by prefix vs hash: prefix sharding keeps a prefix's data on one shard but "a", "the" prefixes run hot — cache absorbs them.
Interviewer will probe
  • Storage size? → Prefixes of top ~100M queries × 10 suggestions ≈ tens of GB — fits in RAM, replicate everywhere.
  • Personalization? → Client-side merge of a small per-user history list with global suggestions.
  • Filtering bad suggestions? → Blocklist applied in the offline build, plus a kill switch at serve time.

Web crawler

Scale assumption: 1B pages/month ≈ 400 pages/s sustained; avg page 500 KB → ~200 MB/s download; billions of seen URLs.

Recipe.
  • Frontier: two-level queues — priority (freshness × pagerank) feeding per-host FIFO queues.
  • Politeness: one connection per host, delay between hits, robots.txt cached per domain — non-negotiable.
  • Fetchers: async I/O workers, DNS cached aggressively (DNS is a hidden bottleneck at 400/s).
  • Dedupe: bloom filter on normalized URL (seen?); simhash on content (near-duplicate pages).
  • Storage: raw HTML → object store; extracted links → frontier; metadata → KV (URL, hash, last-crawl).
  • Traps: max depth, max URLs/domain, URL-length caps — auto-generated infinite spaces are everywhere.

Key trade-offs

  • BFS vs priority order: pure BFS wastes budget on junk; priority by importance/change-rate crawls what matters.
  • Bloom filter false positives: some URLs never crawled vs 10× memory for exact set — accept the tiny FP rate.
Interviewer will probe
  • How do you shard? → Frontier by host-hash so one worker owns a host's politeness state.
  • Recrawl strategy? → Per-URL change-frequency estimate; news hourly, static pages monthly.
  • JS-rendered pages? → Headless-browser fleet ~100× the cost — reserve for the small set that needs it.

Full walkthrough: Web crawler

Top-K trending

Scale assumption: 10M events/s (views/hashtags), top 100 per window (1 min / 1 h / 1 day), answer in <100 ms, small error OK.

Recipe.
  • Ingest: events → Kafka, partitioned by item hash — same item always hits the same counter node.
  • Fast path: count-min sketch + min-heap of K per node per window — fixed memory (~MBs) regardless of cardinality.
  • Merge: each node's local top-K → aggregator merges heaps per window → serve from cache.
  • Windows: ring of 1-min buckets; 1-h = sum of 60 buckets; expire old buckets.
  • Slow path (exact): the same Kafka stream → batch job (Spark) computes exact daily top-K, corrects the dashboard — lambda architecture.

Key trade-offs

  • Exact hash-map counts vs count-min sketch: exact needs memory ∝ distinct items (billions); sketch is fixed-size with small overcount — trending tolerates it.
  • Merged local top-Ks can miss a globally-hot-but-locally-cold item — partition by item hash so each item is counted whole on one node.
Interviewer will probe
  • Why does count-min only overcount? → Hash collisions add, never subtract; take the min across d rows to bound it.
  • Sliding vs tumbling window? → Sum the last N minute-buckets = sliding at bucket granularity — cheap and close enough.
  • K changes to 1000? → Heap size per node grows; sketch unchanged — parameters are independent.

Ride-hailing (Uber)

Scale assumption: 1M concurrent drivers pinging location every 4 s → 250k location writes/s; 100k match requests/min at peak.

Recipe.
  • Location ingest: driver app pings over WebSocket/UDP-ish channel every 4 s; last-known position only — history goes async to Kafka.
  • Geo index: H3/geohash cell → set of driver IDs, in memory (Redis GEO or custom), sharded by cell; a ping is a cell-set move.
  • Matching: query rider's cell + neighbor ring, rank by road-network ETA (not straight-line), offer to best driver with a ~15 s accept timeout, cascade on decline.
  • Lock: driver marked pending during an offer — one offer at a time per driver (no double-dispatch).
  • Trip state: SQL with a state machine (requested→matched→enroute→done) — this is the money record.
  • Surge: per-cell demand/supply ratio from the same counters, published to pricing.

Key trade-offs

  • Ephemeral in-memory locations vs durable store: positions are stale in 4 s anyway — durability buys nothing; rebuild from pings after a crash.
  • Cell size: big cells = fewer shards, hot downtown cells; small cells = more neighbor queries — H3 multi-resolution splits hot areas.
Interviewer will probe
  • Two dispatchers pick the same driver? → Atomic claim (conditional write) on driver state; loser cascades to next candidate.
  • Why not PostGIS for matching? → 250k writes/s of churning point data murders a disk index; the working set is small and ephemeral.
  • City-border rides? → Neighbor-cell queries cross shard boundaries; scatter to the 2–3 shards involved.

File sync / object storage (Dropbox)

Scale assumption: 100M users, avg 10 GB → 1 EB logical; huge dedupe ratio; sync latency target seconds.

Recipe.
  • Chunking: files split into ~4 MB chunks, addressed by SHA-256 of content — dedupe, delta sync, and versioning all fall out of this one choice.
  • Two planes: metadata service (SQL: file→chunk list, versions, sharing) vs block store (S3: chunk blobs) — never mix.
  • Upload: client hashes chunks, asks "which do you already have?", uploads only missing chunks via presigned URLs — bytes bypass the app tier.
  • Sync: client watches FS, computes changed chunks; server notifies other devices via long-poll/WS "namespace changed", they pull the delta.
  • Versioning: a version = a new chunk list; old chunks retained → history is nearly free.
  • Conflicts: no locks — last writer wins on metadata, loser saved as "conflicted copy".

Key trade-offs

  • Fixed-size vs content-defined chunking: fixed is simple but one inserted byte shifts every later chunk; CDC (rolling hash) keeps dedupe under edits.
  • Client-side dedupe check leaks "someone has this file" — rate-limit and salt per account if that matters.
Interviewer will probe
  • Why 4 MB chunks? → Balance: smaller = better dedupe/resume but more metadata rows and requests.
  • 10 GB file upload dies at 90%? → Chunks are the resume unit — re-ask "which are missing", send the tail.
  • Shared folder with 1000 members updated? → One metadata write + notify fan-out; chunks fetched lazily per device.

Video streaming (YouTube-lite)

Scale assumption: 500 h of video uploaded/min; 1B watch-hours/day — views outnumber uploads ~1000:1, and ~all watch bytes come from CDN.

Recipe.
  • Upload: multipart direct-to-S3 via presigned URLs; metadata row created in "processing" state.
  • Transcode: queue → worker fleet; split video into segments, transcode segments in parallel across machines, into a ladder of renditions (240p→4K).
  • Package: HLS/DASH — 2–6 s segments + a manifest listing every rendition.
  • Serve: everything static from CDN; origin is the object store. ABR: player switches rendition per segment based on throughput.
  • Metadata/views: DB for video info; view counts batched via stream, not per-view DB writes.
  • Popular-video problem is solved by the CDN; long-tail misses hit origin behind an origin shield.

Key trade-offs

  • Pre-transcode full ladder vs on-demand: pre-transcode everything popular (compute once, serve billions); lazy/partial ladders for the long tail to save cost.
  • Small segments = faster ABR switching + quicker startup vs more requests and manifest overhead — ~4 s is the industry compromise.
Interviewer will probe
  • Why not stream through your app servers? → Bandwidth: 1B watch-hours/day is Tbps — only a CDN's edge capacity survives it.
  • Live streaming difference? → Same segments, produced in real time; latency = segment length × buffer — hence LL-HLS partial segments.
  • Upload appears "ready" when? → When the lowest rendition finishes — publish progressively, don't wait for 4K.

Payment processing

Scale assumption: 10k payments/s peak; correctness beats latency — losing or double-charging one payment is worse than 500 ms p99.

Recipe.
  • Idempotency: client-generated key stored with the request; retries return the stored result — never a second charge. Pass the same key to the PSP.
  • Ledger: append-only double-entry (debit + credit rows, sum = 0); state machine PENDING→SUCCEEDED/FAILED; never UPDATE amounts.
  • PSP does the card work (PCI scope stays out of your systems); you orchestrate.
  • Webhooks: PSP confirms async; verify signature, dedupe by event id, treat as at-least-once. Don't trust the sync response alone.
  • Timeout on PSP call = UNKNOWN, not failed — query PSP status or wait for webhook before retrying the charge.
  • Reconciliation: nightly job diffs your ledger vs PSP settlement report — the safety net that catches every bug above.
  • Wallet/balance updates and receipts ride an outbox → queue, not the request path.

Key trade-offs

  • Sync authorize vs fully async: the user needs yes/no now → authorize sync with tight timeout; capture/settlement async saga.
  • Exactly-once is a lie at the network level — build at-least-once + idempotency at every hop instead.
Interviewer will probe
  • Client retries after a 504 — did the charge happen? → Idempotency key answers it: same key returns the original outcome.
  • Why append-only ledger? → Auditability and correction-by-compensating-entry; mutable balances can't be audited.
  • Webhook arrives before your DB commit? → Handler upserts by payment id — order-independent state machine transitions.

Ticket booking / flash sale

Scale assumption: 10M users hit an on-sale in the first minute (~150k RPS browse) contending for 50k seats — reads massive, writes scarce and contended.

Recipe.
  • Waiting room: token queue at the edge, admit at measured system capacity — overload becomes fair queueing with an ETA.
  • Browse path: seat map from cache, seconds stale, clearly non-authoritative — absorbs the 150k RPS.
  • Hold: SELECT seat → conditional write (status=FREE→HELD, version check) with a 5-min TTL — optimistic locking; losers get "seat taken".
  • Truth lives in one SQL inventory DB (per event) — strong consistency exactly where money meets scarcity.
  • Confirm: payment success flips HELD→BOOKED (saga with payment); TTL reaper returns abandoned holds.
  • Shard by event_id — one event's contention never touches another's.

Key trade-offs

  • Optimistic vs pessimistic locking: optimistic wins under UI-scale contention (conflicts resolved in ms); row locks held across user think-time would deadlock the sale.
  • Stale browse map vs live: live seat map = 150k RPS on the DB of record; stale + authoritative-check-at-hold is the honest design.
Interviewer will probe
  • How is oversell impossible? → Single-row conditional transition FREE→HELD in one DB — no distributed write path to race.
  • User pays as TTL expires? → Payment confirm re-validates hold atomically; expired → refund path, never a double-booked seat.
  • General-admission (10k identical tickets)? → Decrement a counter (sharded into sub-counters if hot), not per-seat rows.

Metrics / logging pipeline

Scale assumption: 10k hosts × 1k metrics × every 10 s = 1M datapoints/s; logs 1 TB/day; queries want "p99 of X, last 6 h" in <1 s.

Recipe.
  • Collect: agent per host aggregates locally (counters pre-summed per 10 s) — pull (Prometheus-style scrape) or push into Kafka.
  • Buffer: Kafka between producers and storage — absorbs spikes, lets storage restart without loss.
  • Store: TSDB (columnar, delta-of-delta + Gorilla compression ~1.4 B/point) sharded by metric-name hash + time.
  • Downsample: raw 10 s kept ~2 weeks → 1-min rollups 3 months → 1-h rollups 2 years — 99% storage cut, old data stays queryable.
  • Query: fan out to shards, merge; cache dashboard queries; alerting engine evaluates rules on the stream, not the store.
  • Logs are the same pipeline shape: agent → Kafka → indexer (ES/Loki) → tiered retention to S3.

Key trade-offs

  • Pull vs push: pull gives discovery + up/down detection for your own fleet; push for ephemeral jobs, edge, third parties.
  • Pre-aggregate percentiles: you can't average p99s — ship histograms and merge them, or accept per-host-only percentiles.
  • Cardinality is the real capacity limit — one user_id label turns 1k series into 100M; block unbounded labels at ingest.
Interviewer will probe
  • Why a TSDB, not Postgres? → Append-only time-ordered writes + range-scan reads + 10× compression — LSM/columnar is built for exactly this.
  • Losing 10 s of metrics OK? → Yes — say it: at-least-once into Kafka, gaps tolerated; alerts must not silently miss, so alert on absence too.
  • Monitoring the monitoring? → A tiny independent stack (different infra) watches the pipeline itself.
