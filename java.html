1️⃣ JVM & Memory

Everything else in Java sits on top of the JVM. Interviewers use this section to separate "writes Java" from "understands Java": class loading, where objects live, and how garbage collection actually works.

Class Loading & Parent Delegation

Why interviewers ask: it explains ClassNotFoundException vs NoClassDefFoundError, why two copies of the same class can be "different", and how app servers and Spring Boot isolate classes.

Loading a class happens in three phases: Loading (read bytes → Class object), Linking (verify bytecode, prepare static fields with defaults, resolve symbolic refs) and Initialization (run static initializers, in order). Classes are loaded lazily: on first active use.

Three built-in loaders form a hierarchy: Bootstrap (core java.base, native), Platform (JDK modules like java.sql), Application (your classpath). Analogy: a junior engineer who receives a request first asks their manager, who asks their director; only if nobody above can handle it does the junior do it themselves. That is parent delegation: every loader asks its parent first, so core classes can never be shadowed by a malicious java.lang.String on the classpath.

Interview angle: "Can you override java.lang.String by putting your own on the classpath?" No: Bootstrap answers first and the app loader never gets to define it. "Why does Tomcat break delegation?" Web-app loaders look locally first so each WAR can ship its own library versions.

Pitfalls

  • Static initializers run once per loader; a failure is remembered and later uses throw NoClassDefFoundError.
  • Class loader leaks: redeploying a web app while a thread (or ThreadLocal) still references its classes keeps the whole loader alive → Metaspace OOM.

Likely follow-ups

  • What triggers initialization? (new, static method call, static field write, reflection, subclass init, main class.)
  • How does Spring Boot's fat jar load nested jars? (Custom LaunchedURLClassLoader.)
  • Where does class metadata live? (Metaspace since Java 8; PermGen before.)

Java 8 vs 17

Java 9 renamed the Extension loader to Platform loader and stopped using URLClassLoader for the app loader, so casting ClassLoader.getSystemClassLoader() to URLClassLoader now fails.

Runtime Data Areas: Stack vs Heap vs Metaspace

Why interviewers ask: it underpins "is Java pass-by-value?", StackOverflowError vs OutOfMemoryError, and why local variables are thread-safe.

Each thread gets its own PC register and JVM stack of frames (one per method call: local variables, operand stack, return address). All threads share the heap (every object and array) and Metaspace (class metadata, static fields' home). References live on the stack; the objects they point to live on the heap.

public class Demo {
    static int counter = 0;                 // Metaspace (static)

    public static void main(String[] args) {
        int x = 10;                         // primitive → stack frame of main
        Order o = new Order("A1");          // ref on stack, object on heap
        update(o, x);
        System.out.println(o.id + " " + x); // prints "A1-upd 10"
    }

    static void update(Order ord, int n) {
        ord.id = ord.id + "-upd";           // mutates the shared heap object
        n = 99;                             // only this frame's copy changes
        ord = new Order("B2");              // rebinding local ref: caller unaffected
    }
}
  1. Entering main: the frame holds x directly.
  2. new Order allocates on the heap; o is just a reference stored in the frame.
  3. Calling update pushes a new frame. The reference value and the int value are copied: pass-by-value.
  4. Through the copied reference we mutate the one shared object, so main will see it.
  5. n = 99 changes only this frame's slot; x in main is untouched.
  6. Rebinding ord points this frame's slot at a new object. o in main still points at @1.
  7. Frame popped. Output: A1-upd 10. @2 is unreachable and will be collected.

Pitfalls

  • "Java is pass-by-reference" — wrong. It copies the reference value. Rebinding a parameter never affects the caller.
  • Deep recursion (e.g. naive tree DFS on a 1M-node linked chain) overflows the thread stack: switch to an explicit stack.

Likely follow-ups

  • Where do static fields live? (Metaspace holds the class; static object instances are on the heap.)
  • Are string literals on the heap? (Yes, in the heap-resident string pool since Java 7.)
  • What is escape analysis? (JIT can scalar-replace objects that never escape a method, effectively allocating on the stack.)

A class is on the classpath but you get NoClassDefFoundError at runtime. Most likely cause?

c. If initialization fails once (an ExceptionInInitializerError), every later use throws NoClassDefFoundError. a would be a ClassFormatError, b is not an error, and the JIT (d) never rejects classes.

Which statement about method parameters is correct?

b. The walkthrough above shows it: mutating through the copied reference is visible to the caller, but rebinding the parameter (c) is not. Immutability (d) is unrelated to passing semantics.

Practice

Predict the output: static vs instance initialization order

class Parent {
    static { System.out.print("PS "); }
    { System.out.print("PI "); }
    Parent() { System.out.print("PC "); }
}
class Child extends Parent {
    static { System.out.print("CS "); }
    { System.out.print("CI "); }
    Child() { System.out.print("CC "); }
}
public class Main {
    public static void main(String[] a) { new Child(); new Child(); }
}
Tests: class initialization vs object construction
Hint 1
Static blocks run once per class, parent first, before any constructor.
Hint 2
Instance initializer blocks run right after the implicit super() call, before the constructor body.
Reveal solution

Output: PS CS PI PC CI CC PI PC CI CC

First new Child(): initialize Parent (PS) then Child (CS) — once only. Then construct: Child() implicitly calls super(), so Parent's instance block (PI) and constructor (PC) run, then Child's instance block (CI) and constructor (CC). The second new Child() skips the static blocks entirely.
