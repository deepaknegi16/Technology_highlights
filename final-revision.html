2️⃣ DSA: One Must-Do per Topic

Arrays / hashing — Subarray Sum Equals K

Problem: count contiguous subarrays whose sum equals k (negatives allowed).

Tell: "subarray sum" + negatives → prefix sums in a HashMap. Sliding window is wrong here — negatives break its monotonicity.
  • Running sum; a subarray ending here sums to k iff some earlier prefix equals sum − k.
  • Map prefix → count of times seen; seed {0:1} for subarrays starting at index 0.
  • Look up first, then record the current prefix (order matters when k = 0).
int count = 0, sum = 0;
Map<Integer, Integer> seen = new HashMap<>();
seen.put(0, 1);                              // empty prefix
for (int x : nums) {
    sum += x;
    count += seen.getOrDefault(sum - k, 0);
    seen.merge(sum, 1, Integer::sum);
}
return count;

Complexity: O(n) time, O(n) space. Follow-up they'll ask: longest such subarray → store first index of each prefix instead of counts.

String / sliding window — Longest Substring Without Repeating

Problem: length of the longest substring with all distinct characters.

Tell: "longest/shortest substring satisfying X" → grow right, shrink left; window state in a map/array.
  • Track last index of each char; on a repeat inside the window, jump left past it.
  • Window [left..r] is always duplicate-free; answer = max width seen.
  • int[128] beats a HashMap for ASCII — say that.
int[] last = new int[128];
Arrays.fill(last, -1);
int best = 0, left = 0;
for (int r = 0; r < s.length(); r++) {
    char c = s.charAt(r);
    if (last[c] >= left) left = last[c] + 1;  // jump past the duplicate
    last[c] = r;
    best = Math.max(best, r - left + 1);
}
return best;

Complexity: O(n) time, O(1) space (alphabet-bounded). Follow-up they'll ask: "at most K distinct chars" → count map + shrink while size > K.

Deep dive: DSA guide

Two pointers — Container With Most Water

Problem: two lines from a height array form a container with the x-axis; maximize water area.

Tell: sorted array or "best pair at opposite ends" → pointers from both ends, move one inward per step.
  • Area = width × min(height). Moving the taller wall can only shrink area (width down, min capped).
  • So always move the shorter wall — the only move that might help. That's the whole proof; be ready to say it.
int l = 0, r = h.length - 1, best = 0;
while (l < r) {
    best = Math.max(best, (r - l) * Math.min(h[l], h[r]));
    if (h[l] < h[r]) l++; else r--;          // move the shorter wall
}
return best;

Complexity: O(n) time, O(1) space. Follow-up they'll ask: Trapping Rain Water — same two pointers, but track leftMax/rightMax and sum per-cell water.

Binary search — Search in Rotated Sorted Array

Problem: find target in a sorted array rotated at an unknown pivot, O(log n), no duplicates.

Tell: sorted-ish input + O(log n) demanded → binary search on a modified invariant.
  • Key fact: at every mid, at least one half is fully sorted.
  • Identify the sorted half (n[lo] <= n[mid]?), check if target lies inside it, keep that half or the other.
  • Use <= on both range checks; off-by-ones live there.
int lo = 0, hi = n.length - 1;
while (lo <= hi) {
    int mid = (lo + hi) >>> 1;
    if (n[mid] == t) return mid;
    if (n[lo] <= n[mid]) {                     // left half sorted
        if (n[lo] <= t && t < n[mid]) hi = mid - 1; else lo = mid + 1;
    } else {                                     // right half sorted
        if (n[mid] < t && t <= n[hi]) lo = mid + 1; else hi = mid - 1;
    }
}
return -1;

Complexity: O(log n) time, O(1) space. Follow-up they'll ask: with duplicates → when n[lo] == n[mid] == n[hi], shrink both ends; worst case degrades to O(n).

Stack — Valid Parentheses (+ Min Stack twist)

Problem: is a string of ()[]{} balanced and correctly nested?

Tell: "most recent open thing must close first" → LIFO → stack. Nesting, undo, matching = stack.
  • Trick: push the expected closer, so the closing branch is one comparison.
  • Fail cases: pop on empty, mismatch, non-empty at end.
  • Use ArrayDeque, never java.util.Stack (legacy, synchronized) — say it.
Deque<Character> st = new ArrayDeque<>();
for (char c : s.toCharArray()) {
    switch (c) {
        case '(' -> st.push(')');
        case '[' -> st.push(']');
        case '{' -> st.push('}');
        default  -> { if (st.isEmpty() || st.pop() != c) return false; }
    }
}
return st.isEmpty();

Complexity: O(n) time, O(n) space. Follow-up they'll ask: Min Stack — push a pair (val, minSoFar) so getMin() is the top's second field, all ops O(1).

Queue / deque — Sliding Window Maximum

Problem: max of every window of size k, in O(n) total.

Tell: "max/min of each sliding window" → monotonic deque of indexes, values decreasing front→back.
  • Front = current window's max. Pop front when its index leaves the window.
  • Before pushing i, pop everything smaller from the back — they can never be a future max.
  • Each index pushed/popped once → amortized O(1) per element.
Deque<Integer> dq = new ArrayDeque<>();      // indexes, values decreasing
int[] out = new int[n.length - k + 1];
for (int i = 0; i < n.length; i++) {
    if (!dq.isEmpty() && dq.peekFirst() <= i - k) dq.pollFirst();  // expired
    while (!dq.isEmpty() && n[dq.peekLast()] <= n[i]) dq.pollLast();
    dq.addLast(i);
    if (i >= k - 1) out[i - k + 1] = n[dq.peekFirst()];
}
return out;

Complexity: O(n) time, O(k) space — vs O(n log n) with a heap; know why the deque wins. Follow-up they'll ask: sliding window median → two heaps with lazy deletion.

Linked list — Reverse Nodes in k-Groups

Problem: reverse a list k nodes at a time; a final group shorter than k stays as-is.

Tell: any list-rewiring problem = the 3-pointer reverse loop (prev/head/next) plus bookkeeping. Recursion keeps k-groups clean.
  • Count k nodes ahead; fewer → return head untouched.
  • Recurse on the rest first, then reverse this group onto that result.
  • Iterative version: dummy head + reconnect group ends — mention it for O(1) space.
public ListNode reverseKGroup(ListNode head, int k) {
    ListNode node = head;
    for (int i = 0; i < k; i++) {            // is a full group present?
        if (node == null) return head;       // no → leave the tail alone
        node = node.next;
    }
    ListNode prev = reverseKGroup(node, k);  // rest is already done
    for (int i = 0; i < k; i++) {            // classic 3-pointer reverse
        ListNode next = head.next;
        head.next = prev; prev = head; head = next;
    }
    return prev;
}

Complexity: O(n) time, O(n/k) recursion stack. Follow-up they'll ask: cycle detection — Floyd fast/slow pointers; they meet inside a cycle, then reset one to head and walk both by 1 to find the cycle start.

Tree — Level Order + Lowest Common Ancestor

Problem pair: print a binary tree level by level; find the deepest node that has both p and q beneath (or equal to) it.

Level order tell: "by level / zigzag / right view" → BFS with a queue.
  • Snapshot int size = q.size() per round; drain exactly that many → one list per level.
  • Zigzag/right-view are the same loop with a reverse flag or "last of level".
LCA tell: "common ancestor / distance between nodes" → post-order DFS returning found-ness upward.
TreeNode lca(TreeNode root, TreeNode p, TreeNode q) {
    if (root == null || root == p || root == q) return root;
    TreeNode l = lca(root.left, p, q);
    TreeNode r = lca(root.right, p, q);
    if (l != null && r != null) return root;   // split point = answer
    return l != null ? l : r;                    // bubble the found side up
}

Complexity: both O(n) time; BFS O(width), DFS O(height) space. Follow-up they'll ask: LCA with parent pointers → walk both up like intersecting linked lists, O(1) space.

BST — Validate BST + Kth Smallest

Problem pair: is a binary tree a valid BST; find the kth smallest element in one.

Tell: BST anywhere → think "inorder = sorted". Both problems fall out of that.
  • Classic trap: checking only child vs parent — fails for a grandchild violating a grandparent. Pass down range bounds.
  • Use long bounds (or null Integers) so Integer.MIN/MAX_VALUE node values don't break edges.
  • Kth smallest: inorder walk, decrement k, answer when k hits 0 — stop early.
boolean valid(TreeNode n, long lo, long hi) {   // start: MIN, MAX
    if (n == null) return true;
    if (n.val <= lo || n.val >= hi) return false;
    return valid(n.left, lo, n.val) && valid(n.right, n.val, hi);
}
// kth smallest: inorder DFS, if (--k == 0) answer = n.val;

Complexity: O(n) / O(h) for validate; kth is O(h + k). Follow-up they'll ask: kth queried often with inserts → store subtree sizes in nodes → O(log n) per query.

Heap — Merge K Sorted Lists

Problem: merge k sorted linked lists into one sorted list.

Tell: "k sorted sources" or "top-K / Kth largest of a stream" → heap of size k.
  • Heap holds one head node per list — the global min is always in there.
  • Poll min, append, push its next. n total nodes, each through the heap once.
  • Top-K rule: K largest → min-heap of size K (evict the smallest) — interviewers love this inversion.
PriorityQueue<ListNode> pq = new PriorityQueue<>((a, b) -> a.val - b.val);
for (ListNode l : lists) if (l != null) pq.add(l);
ListNode dummy = new ListNode(0), tail = dummy;
while (!pq.isEmpty()) {
    ListNode min = pq.poll();
    tail.next = min; tail = min;
    if (min.next != null) pq.add(min.next);
}
return dummy.next;

Complexity: O(n log k) time, O(k) space. Follow-up they'll ask: divide-and-conquer pairwise merge — same O(n log k), no heap; and the comparator overflow trap (a.val - b.val → use Integer.compare).

Graph — Number of Islands + Course Schedule

Problem pair: count connected land regions in a grid; can n courses with prerequisites all be taken (cycle check)?

Islands tell: grid + "connected regions" → flood fill.
  • Scan cells; each unvisited '1' = +1 island, then DFS/BFS sink the whole component (mark '0').
  • Grid is the graph — no adjacency list; 4-direction deltas array.
Course Schedule tell: "prerequisites / build order / can finish" → topological sort (Kahn's BFS).
// Kahn: adj + indegree built from prereq edges
Deque<Integer> q = new ArrayDeque<>();
for (int i = 0; i < n; i++) if (indeg[i] == 0) q.add(i);
int seen = 0;
while (!q.isEmpty()) {
    int u = q.poll(); seen++;
    for (int v : adj[u]) if (--indeg[v] == 0) q.add(v);
}
return seen == n;                     // seen < n → cycle → impossible

Complexity: both O(V+E) time. Follow-up they'll ask: return the actual order (record polls); islands follow-up — count distinct island shapes → canonical path signature per DFS.

DP — Coin Change (+ LIS one-liner)

Problem: fewest coins (unlimited reuse) summing to amount; −1 if impossible.

Tell: "min/max ways to reach a total, items reusable" → unbounded knapsack, 1-D bottom-up.
  • State: dp[a] = min coins to make amount a. Transition: best over dp[a − coin] + 1.
  • Greedy fails — coins {1,3,4}, amount 6: greedy 4+1+1=3 vs DP 3+3=2. Have this counter-example ready.
  • Fill with amount+1 as infinity; unreachable stays > amount.
int[] dp = new int[amount + 1];
Arrays.fill(dp, amount + 1);                 // "infinity"
dp[0] = 0;
for (int a = 1; a <= amount; a++)
    for (int c : coins)
        if (c <= a) dp[a] = Math.min(dp[a], dp[a - c] + 1);
return dp[amount] > amount ? -1 : dp[amount];

Complexity: O(amount × coins) time, O(amount) space. LIS one-liner: keep a tails array; binary-search each element's insertion point and overwrite → O(n log n); array length = LIS length.

Follow-up they'll ask: count ways instead of min coins → same loop, dp[a] += dp[a−c], coins outer to avoid counting permutations.

3️⃣ Java in 20 Answers

JVM & GC (5)

  • Heap layout in one breath? — Young gen (eden + two survivors, most objects die here, cheap minor GCs) + old gen (survivors promoted after aging); classes/metadata live off-heap in metaspace; thread stacks are per-thread and hold frames + references.
  • Which GC and why? — G1 is the default: region-based, pause-target driven, fine for most services. ZGC when you need <1 ms pauses on huge heaps; Parallel when pure throughput (batch) beats latency. Say "I'd change GC only after measuring".
  • OOM triage? — -XX:+HeapDumpOnOutOfMemoryError, open the dump in MAT/JFR, find dominator-tree heavyweights; usual suspects: unbounded caches/maps, listener leaks, ThreadLocals in pools. Metaspace OOM → classloader leak (redeploys).
  • JIT in two lines? — Bytecode is interpreted first; hot methods are compiled (C1→C2), inlined, and speculatively optimized with deoptimization as a safety net. That's why benchmarks need warm-up (use JMH).
  • Class loading? — Load → link (verify/prepare/resolve) → initialize (statics, <clinit>), lazily on first use; parent-delegation: app loader asks platform asks bootstrap first, so you can't shadow java.lang.String.

Deep dive: Java guide — JVM internals · OOM playbook

Collections (5)

  • HashMap internals? — Array of buckets, index = hash & (n−1) (n is a power of 2, hash is spread by XOR of high bits); collisions chain as a list, treeify to red-black at 8 nodes (when table ≥ 64); resize doubles at load factor 0.75 and splits each bucket into two.
  • Fail-fast means? — Iterators snapshot modCount; structural modification outside the iterator throws ConcurrentModificationException on a best-effort basis — it's a bug detector, not a thread-safety guarantee. Remove via the iterator or removeIf.
  • ConcurrentHashMap? — Lock-free reads, CAS for empty-bucket inserts, per-bucket synchronized for the rest; no table-wide lock, no CME (weakly consistent iterators). Use compute/merge for atomic read-modify-write; size() is an estimate under concurrency.
  • ArrayList vs LinkedList honestly? — ArrayList wins ~always: O(1) indexed access, cache-friendly, amortized O(1) append. LinkedList's O(1) insert needs an iterator already positioned; per-node allocations wreck cache locality. Real answer: "ArrayList, or ArrayDeque for queue ends".
  • When TreeMap? — Sorted keys with range queries: firstKey/floorKey/headMap/subMap — think leaderboards, time-indexed lookups, "nearest entry ≤ x". O(log n) everything; comparator must be consistent with equals.

Deep dive: HashMap internals · Collections section

Concurrency (6)

  • volatile vs synchronized? — volatile = visibility + ordering for one variable, no atomicity (count++ still races). synchronized = mutual exclusion + visibility for a block. Rule: single flag → volatile; compound state or check-then-act → lock or atomics.
  • Happens-before in one breath? — The JMM only guarantees a read sees a write if a happens-before chain links them: program order, monitor unlock→lock, volatile write→read, Thread.start()/join(). No chain → no guarantee, regardless of wall-clock timing.
  • Thread pool sizing? — CPU-bound: ~cores. I/O-bound: cores × (1 + wait/compute) — or stop sizing and use virtual threads. Always bound the queue and name the pool; unbounded queues turn overload into OOM instead of rejection.
  • CompletableFuture? — Compose async steps: supplyAsync → thenApply/thenCompose → exceptionally; combine with thenCombine/allOf. Traps: default ForkJoin commonPool for blocking work (pass an executor), and forgetting join()/exception handling swallows failures.
  • Virtual threads? — JDK 21 user-mode threads: millions of cheap, blockable threads mounted on few carriers — thread-per-request without pools for I/O-bound services. Pinning caveat: synchronized around blocking I/O pins the carrier (pre-24) → prefer ReentrantLock there. No help for CPU-bound work.
  • Deadlock diagnosis? — jstack/thread dump; the JVM prints "Found one Java-level deadlock" with both cycles. Fix: global lock ordering, tryLock with timeout, or shrink to one lock. Mention livelock/starvation as the cousins.

Deep dive: Concurrency section · JMM · Virtual threads

Language & streams (4)

  • Records & sealed? — record = nominal immutable data carrier: final fields, canonical constructor (validate there), equals/hashCode/toString generated. sealed = closed hierarchy → compiler-checked exhaustive switch pattern matching; together they give you ADTs.
  • Streams laziness + parallel trap? — Intermediate ops build a recipe; nothing runs until a terminal op, then one fused pass (short-circuits with findFirst/limit). parallelStream() uses the shared commonPool: wrong for small data, I/O, or stateful lambdas — measure before using, never in request paths.
  • equals/hashCode contract? — Equal objects must have equal hash codes (reverse not required). Break it and hash collections lose your object: stored in bucket for old hash, looked up in bucket for new. Corollaries: never mutate a key's hash fields; override both or neither.
  • String pool? — Literals are interned and shared in a heap pool: "a" == "a" is true, new String("a") makes a fresh object. Always compare with equals; compile-time constant concat is pooled, runtime concat is not.

Deep dive: Records · Parallel streams · equals/hashCode · String pool

4️⃣ Spring Boot in 20 Answers

Core container (5)

  • Bean lifecycle in one breath? — Scan/read definitions → BeanFactoryPostProcessors tweak definitions → for each bean: instantiate → populate dependencies → Aware callbacks → BPP before-init → @PostConstruct → afterPropertiesSet → init-method → BPP after-init (AOP proxies born here) → use → @PreDestroy on shutdown.
  • @Component vs @Bean? — @Component: class you own, found by scanning. @Bean: factory method inside @Configuration — for third-party types or when construction needs logic. Same container result, different registration route.
  • Circular dependencies? — A needs B needs A. Singleton field/setter injection survives via the early-reference third-level cache; constructor injection fails fast (Boot 2.6+ rejects cycles by default). Right fix: break the cycle (extract a third bean), not @Lazy duct tape.
  • @Configuration proxying? — Full mode CGLIB-subclasses the config class so @Bean-method calls between beans return the container singleton. In lite mode (@Component + @Bean, or proxyBeanMethods=false) this.otherBean() is a plain call → a second unmanaged instance.
  • Scopes gotcha? — Singleton (default) and prototype; injecting a prototype into a singleton freezes one instance forever — fix with ObjectProvider or scoped proxy. Request/session scopes exist for web state.

Deep dive: Bean lifecycle · Circular deps · @Component vs @Bean

Web & data (5)

  • Request flow in one breath? — Servlet container → security/other filters → DispatcherServlet → HandlerMapping picks the controller method → interceptors preHandle → argument resolvers bind/validate → your method → return value handled (Jackson via HttpMessageConverter) → exception resolvers / @ControllerAdvice if thrown.
  • @Transactional rules? — Works via proxy: public external calls only; rollback on unchecked by default (checked needs rollbackFor); keep transactions short, never call remote services inside one; readOnly=true for queries; propagation REQUIRED default, REQUIRES_NEW for audit-must-commit.
  • Self-invocation trap? — this.otherMethod() bypasses the proxy → no transaction/cache/async applied. Fix: move the method to another bean, or inject self/use TransactionTemplate. Same trap for @Cacheable and @Async.
  • N+1 fixes? — Detect: SQL logging / p6spy shows 1 parent query + N child queries. Fix: join fetch in JPQL, @EntityGraph, or batch fetching (default_batch_fetch_size). Root cause: lazy association touched in a loop; DTO projections skip entities entirely.
  • Validation? — @Valid on the @RequestBody param triggers Bean Validation (@NotNull, @Size…) → MethodArgumentNotValidException → map to 400 in @ControllerAdvice. Nested objects need @Valid on the field; class-level rules via custom constraint.

Deep dive: Request lifecycle · @Transactional · N+1

Security & AOP (5)

  • Filter chain in one breath? — One servlet filter (FilterChainProxy) delegates to an ordered SecurityFilterChain: CORS → CSRF → auth filters (JWT/Basic/form) populate the SecurityContext → exception translation (401 vs 403) → authorization filter checks rules last. Configured as a SecurityFilterChain bean, not the old adapter.
  • JWT flow? — Login issues a signed token (claims + expiry); each request sends Authorization: Bearer; a once-per-request filter validates signature + expiry and sets the Authentication; server stays stateless (SessionCreationPolicy.STATELESS). Revocation is the weak spot → short TTL + refresh tokens.
  • 401 vs 403? — 401 unauthenticated (who are you?) from the entry point; 403 authenticated but not allowed (access denied handler). Interviewers use it to test if you understand the exception-translation filter.
  • AOP proxy limitations? — Spring AOP = runtime proxies: only public method calls entering the bean from outside are advised. Self-invocation, private/final methods, and field access are invisible. JDK proxy needs an interface; CGLIB subclasses (default in Boot).
  • @PreAuthorize? — Method security (@EnableMethodSecurity) with SpEL: hasRole('ADMIN'), #id == principal.id. Same proxy caveats; prefer it on service layer, URL rules for coarse gates.

Deep dive: Security architecture · JWT · Self-invocation

Boot & ops (5)

  • Auto-configuration in one breath? — @EnableAutoConfiguration imports config classes listed in AutoConfiguration.imports from every starter; each applies only if its @ConditionalOn… (class present, bean missing, property set) holds — so your own @Bean silently wins over the default. Debug with --debug condition report.
  • Property precedence top-5? — Highest first: command-line args → OS env vars → profile-specific application-{profile}.yml → application.yml outside the jar → inside the jar. Devops overrides beat packaged defaults; that's the whole design.
  • Actuator? — Production endpoints: /health (liveness/readiness groups for k8s), /metrics via Micrometer, /env, /threaddump, /heapdump. Expose selectively, lock behind auth — /env and /heapdump leak secrets.
  • Test slices? — @WebMvcTest (controllers + MockMvc, no services), @DataJpaTest (repos + rollback tx + embedded/Testcontainers DB), @SpringBootTest full context last resort. Slices load less → faster, sharper failures; mock the missing edges with @MockitoBean.
  • Startup too slow — what do you check? — Condition evaluation report, lazy init flag, context caching in tests, and who's doing I/O in @PostConstruct. Shows ops maturity in one answer.

Deep dive: Auto-configuration · Property precedence · Testing

5️⃣ Microservices in 15 Answers

Communication & data (5)

  • Sync vs async — the decision? — Sync (REST/gRPC) when the caller needs the answer to proceed (auth check, price quote). Async (events/queues) when it doesn't (notifications, projections, anything retryable) — async decouples uptime and absorbs spikes, at the cost of eventual consistency and harder debugging.
  • Saga vs 2PC? — 2PC holds locks across services while a coordinator votes — blocks on coordinator failure, kills availability; nobody runs it across microservices. Saga = sequence of local transactions + compensating actions on failure. Choreography (events) for few steps; orchestration (explicit state machine) when the flow needs visibility.
  • Outbox pattern? — "Write DB + publish event" is two systems, no atomicity. Fix: write the event into an outbox table in the same local transaction; a relay (poller or CDC/Debezium) publishes it after commit. Guarantees at-least-once → consumers must dedupe.
  • Idempotency? — Retries + at-least-once mean everything arrives twice eventually. Client sends an idempotency key; server does check-and-record atomically (unique constraint / Redis SETNX) and replays the stored response on duplicates. Natural idempotency (state-based updates) beats bolted-on where possible.
  • Who owns the data? — One service, one database; others get data via API or subscribed events (local read models). Shared tables couple deploys and schemas — the #1 microservices smell.

Deep dive: Sagas · Outbox · Idempotency

Resilience & scale (5)

  • Timeouts + retries + circuit breaker in one answer? — Every remote call gets a timeout shorter than your own SLA budget; retries only on idempotent ops, few, with exponential backoff + jitter (retry storms amplify outages); a circuit breaker trips after a failure ratio, fails fast while open, half-opens to probe. Order matters: timeout bounds one call, retry bounds attempts, breaker bounds the epidemic. Plus bulkheads: separate pools per dependency.
  • Rate limiting? — Token bucket (allows bursts, refill = sustained rate) is the default; sliding window counter for smoother fairness. Enforce at the gateway per user/API-key; return 429 + Retry-After. Distributed: counters in Redis (Lua for atomicity), accept slight over-admission.
  • Cache-aside + stampede? — Read: cache → miss → DB → set with TTL. Write: update DB, invalidate (don't update) cache. Stampede on hot-key expiry: single-flight lock (one loader, rest wait), jittered TTLs, or serve-stale-while-refreshing. Say "cache is a copy, DB is truth".
  • Consistent hashing one-liner? — Nodes and keys hash onto a ring; a key belongs to the next node clockwise, so adding/removing a node remaps only ~1/N of keys (vs nearly all with mod-N); virtual nodes smooth the load.
  • Scaling a stateless service? — Horizontal replicas behind an LB; state pushed out to Redis/DB; scale on a leading signal (queue depth, RPS per pod) not just CPU; know your per-pod capacity number from a load test.

Deep dive: Timeouts & retries · Stampede · Rate limiting

Operations (5)

  • Observability's 3 signals? — Metrics (aggregates, cheap, alert on them: RED — rate, errors, duration), logs (structured JSON, per-event detail, correlation ID on every line), traces (one request's path across services with per-hop timing). Alert on symptoms users feel (SLO burn), not on causes.
  • Deployment safety? — Rolling for routine; canary (1% → watch error rate/p99 → ramp) for risk; blue-green for instant rollback. Non-negotiables: health/readiness probes gate traffic, DB migrations backward-compatible (expand → migrate → contract), feature flags decouple release from deploy.
  • Multi-region in one breath? — Route users to the nearest region (GeoDNS/anycast); active-active for stateless tiers; data is the hard part — async replication + region-local reads, writes either home-region-pinned or accept conflict resolution. Failover = DNS/traffic shift + promoting replicas; practice it or it doesn't exist.
  • How do you debug high p99? — p50 fine + p99 bad = a slow minority: check GC pauses, connection-pool exhaustion, one slow shard/hot key, cold caches, retry amplification. Path: dashboards → exemplar traces of slow requests → find the hop that ate the time → its saturation metric. Say "tail latency amplifies with fan-out" — one slow dependency in 10 parallel calls owns your p99.
  • Config & secrets? — Externalized config (env/config server), secrets in a vault not git, per-env overrides via the precedence chain, and audit who read what.

6️⃣ Low-Level Design Speed-Run

SOLID + the 8 patterns cheat

SOLID in five lines.
  • Single responsibility — one reason to change per class; if the name has "And", split it.
  • Open/closed — add behavior by adding types (new Strategy/subclass), not by editing switch blocks.
  • Liskov — subtype must honor the base contract; a Square that breaks Rectangle's setters is the classic violation.
  • Interface segregation — many small interfaces; no client forced to depend on methods it ignores.
  • Dependency inversion — depend on abstractions, inject implementations (what Spring DI does for you).
PatternOne-line use case
SingletonOne shared stateless/coordinating instance — ParkingLot, config, connection pool (enum or holder idiom, or let the DI container do it).
FactoryCreation varies by type/config — VehicleFactory.create(type), payment-method creation, RateLimiter algo from config.
StrategySwap an algorithm at runtime — fee calculation, split logic, dispatch policy, retry policy.
ObserverNotify N listeners of an event without coupling — seat released, price drop, elevator arrived.
DecoratorLayer optional behavior over the same interface — metrics/logging around a RateLimiter, toppings on an order.
BuilderMany optional constructor params — immutable Booking/Request objects with readable construction.
AdapterWrap a foreign API into your interface — Stripe/PayPal behind one PaymentGateway.
StateBehavior depends on lifecycle state — elevator (moving/idle/doors-open), order status transitions, seat FREE→HELD→BOOKED.

LLD 1 — Parking Lot

Requirements (get sign-off first):
  • Multiple floors; spot sizes (bike/compact/large); vehicle parks in a fitting spot.
  • Ticket on entry, fee on exit — fee policy varies (hourly, flat, weekend).
  • Real-time free-spot count per floor/size.
enum SpotSize { BIKE, COMPACT, LARGE }
interface Vehicle { SpotSize required(); String plate(); }

class ParkingSpot { SpotSize size; boolean free; }
class ParkingFloor { Map<SpotSize, Deque<ParkingSpot>> freeSpots;
    Optional<ParkingSpot> acquire(Vehicle v); }

interface FeeStrategy { BigDecimal fee(Ticket t); }        // hourly, flat…

class ParkingLot {                                          // singleton
    List<ParkingFloor> floors; FeeStrategy pricing;
    Ticket enter(Vehicle v);          // find spot, stamp entry time
    BigDecimal exit(Ticket t);        // pricing.fee(t), free the spot
}
Patterns & why:
  • Strategy for fees — pricing changes without touching ParkingLot (open/closed).
  • Singleton ParkingLot; Factory if vehicle/spot creation grows variants.
  • Free spots per size in a Deque/heap — O(1) allocate beats scanning floors.

Follow-up they'll ask: concurrency — two cars, one spot: make acquire atomic (synchronized per floor or ConcurrentLinkedDeque.poll); nearest-spot allocation → min-heap by distance per size.

LLD 2 — Elevator System

Requirements:
  • N elevators, M floors; hall calls (floor + direction) and cabin calls (target floor).
  • Assign calls to the best elevator; serve stops in sweep order, not FIFO.
  • States: idle, moving up/down, doors open; capacity/overload flag.
enum Direction { UP, DOWN, IDLE }

class Elevator {
    int floor; Direction dir;
    TreeSet<Integer> upStops = new TreeSet<>();     // sorted sweep
    TreeSet<Integer> downStops = new TreeSet<>(Comparator.reverseOrder());
    void addStop(int f);
    void step();               // move one floor; open doors if f is a stop
}

interface DispatchStrategy { Elevator pick(List<Elevator> all, int floor, Direction d); }

class ElevatorController {     // receives hall calls, delegates to strategy
    DispatchStrategy strategy; List<Elevator> cars;
}
Patterns & why:
  • State — behavior per state (a moving car ignores door commands); avoids nested-if soup.
  • Strategy for dispatch — nearest-car vs load-balanced swappable; the LOOK/SCAN sweep (finish this direction, then reverse) is the answer they want, and TreeSet.ceiling/floor gives the next stop.
  • Observer — floors/displays subscribe to elevator position events.

Follow-up they'll ask: why not FIFO? (starves middle floors, zigzags); how to handle a call while moving opposite → queue it in the other TreeSet for the return sweep.

LLD 3 — Splitwise

Requirements:
  • Users add expenses paid by one, split among many — equal, exact amounts, or percentages.
  • Anyone can view net balances ("who owes whom how much").
  • Settle-up suggests the minimum number of transactions.
record Expense(User paidBy, BigDecimal amount,
               List<User> among, SplitStrategy split) {}

interface SplitStrategy {                       // EQUAL, EXACT, PERCENT
    Map<User, BigDecimal> shares(Expense e);    // validates sums to total
}

class Ledger {
    Map<User, BigDecimal> net = new HashMap<>();   // + is owed, − owes
    void apply(Expense e);        // payer += amount; each sharer −= share
    List<Txn> settle();           // greedy: max debtor pays max creditor
}
Patterns & why:
  • Strategy per split type — validation lives with the strategy (percents sum to 100, exacts sum to total).
  • Net-balance map, not pairwise matrix — settle-up is greedy two-heap matching (max debtor ↔ max creditor), ≤ n−1 transactions.
  • BigDecimal for money, and say who eats the leftover paisa on 100/3 — rounding policy is a real requirement.

Follow-up they'll ask: is minimum-transaction settling optimal? (greedy is a good heuristic; true minimum is NP-hard — knowing that is the senior answer); groups + simplify-debts toggle; concurrent expense adds → per-group lock or event log.

LLD 4 — BookMyShow (seat locking)

Requirements:
  • Browse shows, pick seats from a live seat map.
  • Selected seats lock for 5 min while paying; expire back to free if unpaid.
  • Two users must never book the same seat — correctness over latency here.
enum SeatState { FREE, HELD, BOOKED }
class Seat { String id; SeatState state; long version; }

class SeatHold { List<Seat> seats; User user; Instant expiresAt; }

interface SeatLockService {
    Optional<SeatHold> hold(Show show, List<String> seatIds, User u);
    void release(SeatHold h);                    // TTL reaper calls this
}

class BookingService {
    Booking confirm(SeatHold h, PaymentResult p);  // HELD → BOOKED atomically
}
Patterns & why:
  • State — FREE→HELD→BOOKED with legal transitions only; HELD→FREE on TTL expiry.
  • Optimistic locking (version check / conditional update) on the hold — all seats in one transaction, any conflict rolls back the whole hold.
  • Facade BookingService orchestrates hold + payment + confirm; Observer notifies waitlist on release.

Follow-up they'll ask: payment succeeds as the hold expires → confirm re-validates the hold atomically, else refund; where does the lock live at scale → DB conditional update or Redis SETNX+TTL, single source of truth per show.

LLD 5 — Rate Limiter (class design)

Requirements:
  • boolean allow(clientKey) — N requests per window per client, thread-safe.
  • Pluggable algorithm (token bucket, sliding window log/counter) chosen by config.
  • Bursts allowed up to capacity; memory bounded per client.
interface RateLimiter { boolean allow(String key); }

class TokenBucket implements RateLimiter {
    final long capacity, refillPerSec;
    final ConcurrentHashMap<String, Bucket> buckets = new ConcurrentHashMap<>();
    // Bucket { double tokens; long lastNanos; }  — refill lazily:
    // tokens = min(capacity, tokens + elapsedSec * refillPerSec)
    public boolean allow(String key) {
        return buckets.computeIfAbsent(key, k -> new Bucket())
                      .tryConsume();               // synchronized per bucket
    }
}
class RateLimiterFactory { static RateLimiter of(Config c); }
class MeteredLimiter implements RateLimiter { /* wraps + counts 429s */ }
Patterns & why:
  • Strategy — algorithms behind one interface; callers never know which.
  • Factory reads config → algorithm; Decorator layers metrics/logging without touching core logic.
  • Lazy refill on access (no timer threads); per-bucket lock, not a global one — say why.

Follow-up they'll ask: distributed version → counters in Redis with a Lua script for atomic check-and-decrement; token bucket vs sliding window trade-off (bursts vs smoothness); eviction of idle client buckets (LRU / expireAfterAccess).

Deep dive: Rate limiter design · Algorithms

Subarray Sum Equals K with negative numbers — why not a sliding window?

c. The window trick needs "expand → metric moves one way". With negatives it doesn't, so seen.getOrDefault(sum - k, 0) over prefix counts is the tool.

You need the K largest elements of a huge stream. Which heap?

b. The min-heap's root is the "weakest member of the club" — anything bigger replaces it. O(n log K) time, O(K) memory; a max-heap of everything is O(n) memory.

When does a HashMap bucket become a red-black tree?

c. Both thresholds matter. Load factor 0.75 governs resize, not treeify. CHM treeifies too, so d is wrong.

A @Transactional method is called via this.method() from another method in the same bean. What happens?

d. Spring AOP advises calls that enter through the proxy; this is the raw object. Same trap for @Cacheable and @Async. Fix: move the method to another bean.

Why saga over 2PC for an order → payment → inventory flow across services?

a. The saga's price is intermediate states being visible and compensations you must write — say that trade-off out loud in the interview.

A hot cache key expires and 5,000 requests hit the DB at once. Best fix?

b. This is a stampede (dog-pile). One loader + jitter (or refresh-ahead) removes the thundering herd; longer TTLs just delay it and add staleness.

Fee calculation in your Parking Lot must support hourly, flat, and weekend pricing, selectable at runtime. Which pattern?

c. Interchangeable algorithms behind one interface = Strategy. Decorator would stack behaviors (e.g. surge on top of hourly); template method fixes the skeleton at compile time.

In Coin Change, what does dp[a] mean and why fill with amount + 1?

b. Smallest coin is ≥ 1, so a real answer never exceeds amount coins — anything larger still means "unreachable", hence the final dp[amount] > amount ? -1 : dp[amount].
